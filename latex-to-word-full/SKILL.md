# LaTeX/Markdown to a functional Word document

## Outcome

Produce a DOCX that remains editable and behaves like a real Word document:

- headings, captions, table numbers, equation numbers, citations, and bibliography numbers are generated or linked rather than typed twice;
- equations remain native Word math/OMML whenever the conversion path supports it, and are never rasterized silently;
- figures and tables retain captions, labels, readable sizing, and sensible pagination;
- tables have consistent semantic alignment and, when requested, an academic three-line layout;
- the document is rendered to PDF/PNG and checked page by page before delivery;
- the source files, reference template, and intermediate artifacts are not overwritten unless the user explicitly asks for in-place replacement.

This skill is appropriate for `.tex` projects, Markdown manuscripts, Pandoc-compatible formats, and mixed projects containing figures, `.bib` files, supplementary data, or an existing DOCX template.

## First decisions

1. Inventory the source project before authoring. Run `scripts/inspect_latex_project.py` for a quick machine-readable inventory, then inspect the source preamble, bibliography files, figure directories, and any custom macros that affect semantics.
2. If the user supplied a DOCX template or manually formatted version, treat it as a style reference: preserve its page size, margins, fonts, paragraph styles, heading hierarchy, caption styles, and table conventions, but regenerate the changed content from the current source.
3. If no template is supplied, state the assumptions and create a coherent academic default. Prefer the source class/preamble where it gives a clear signal; otherwise use a consistent paper size, margins, body font, heading hierarchy, caption style, reference style, and table widths. Do not pretend that an unobservable personal formatting preference was recovered.
4. Choose a conversion route based on source complexity:
   - use Pandoc or another semantic converter when it preserves the required math and reference structure;
   - use a custom parser/generator with `python-docx` and OOXML post-processing when exact style control, Word fields, or special tables are important;
   - use a hybrid route when Pandoc handles paragraphs/math well but custom code is needed for captions, fields, tables, or template styles.

## Required workflow

### 1. Build a semantic intermediate model

Do not convert the source by concatenating extracted text. Represent the manuscript as ordered blocks such as title, authors, abstract, heading, paragraph, list, equation, figure, table, and reference entry. Maintain maps for:

- source labels → stable Word bookmark names;
- citation keys → bibliography entry numbers;
- figure/table/equation sequence names → displayed numbers;
- source asset paths → copied or embedded DOCX media.

Parse balanced groups and environments rather than using a single broad regular expression for nested LaTeX. Preserve inline emphasis, code, symbols, Unicode, non-breaking spaces, and escaped punctuation. If a macro cannot be interpreted, keep its visible content and report the unsupported macro instead of dropping it.

### 2. Generate editable Word structures

Use a template when available; otherwise create styles explicitly. Keep source numbering out of visible heading/caption text when Word numbering or fields will generate it. In particular, never combine a manually typed `4.3.` with a Word list that also emits `4.3.`.

Use the following invariants:

- Heading numbering is generated by one mechanism only. Prefer a multilevel Word list linked to heading styles, or use stable displayed numbers when a true list cannot be created; never mix both.
- Captions are centered and use a `SEQ Figure`, `SEQ Table`, or equivalent field wrapped in a bookmark. The caption text is separate from the generated number.
- Cross-references use `REF` fields to bookmarks for figures, tables, equations, and bibliography entries. Static numbers may be used only when the user explicitly accepts a non-updating export.
- Citations resolve to the same bibliography numbering map used by the reference list. Report every unresolved citation or label.
- Equations use native OMML/math objects when available. If a fallback is unavoidable, keep the equation editable as structured text and disclose the limitation; do not replace it with a screenshot without approval.
- Figures are inserted as images with controlled width and centered alignment. Keep a figure with its caption, and allow the following paragraph to use remaining space when the layout permits.
- Body paragraphs must not inherit an unintended `keep_with_next` chain. Apply `keep_with_next` to headings and captions only where useful, and explicitly clear it for ordinary body paragraphs, abstracts, keywords, and references.
- Do not carry a template's hidden `pageBreakBefore` into every top-level heading. Preserve intentional section breaks, but clear accidental inherited page breaks.

### 3. Format tables semantically

Treat table data as cells, not as an image or a tab-separated paragraph. Normalize lightweight source wrappers such as `\\textbf{...}` before deciding alignment, while preserving the requested bold/italic appearance.

For an academic three-line table:

- use a single top rule, a lighter header rule, and a single bottom rule;
- set left/right/inside-horizontal/inside-vertical borders to `nil` so vertical gridlines cannot reappear from a template style;
- center the header row;
- center categorical index columns such as `Type` or `Top-K`;
- left-align prose cells and right-align numeric, percentage, fraction, dash, and `N/A` cells;
- apply the same alignment rule to bold and non-bold cells;
- repeat the header on continuation pages and keep short tables intact where possible;
- prevent a row from splitting across pages and use sensible column widths and cell margins.

Inspect the resulting OOXML, because assigning `Table Grid` and then changing only the visual style often leaves hidden vertical or inside borders behind.

### 4. Render and inspect

Rendering is part of the conversion, not an optional afterthought. Use the document-rendering skill/tool when available. On Windows, a local Microsoft Word PDF export is a valid fallback when LibreOffice is unavailable; on other systems use LibreOffice or the available DOCX renderer. Convert the PDF to page PNGs and inspect every page, not only the first and last pages.

For each page check:

- duplicate heading or caption numbers;
- clipped equations, figures, captions, or table borders;
- large unexplained blank regions after figures/tables;
- headings stranded at page bottoms;
- tables with inconsistent cell alignment, accidental vertical rules, or split short tables;
- bibliography entries split across pages or isolated headings;
- field placeholders, stale cross-reference values, missing images, and font substitutions.

When a layout defect is found, fix the generation rule or style source and rerender. Do not manually patch only one page in the final DOCX unless the exception is intentional and documented.

### 5. Run structural checks before delivery

Run `scripts/validate_docx.py` on the final output. At minimum verify:

- the DOCX ZIP is intact and `python-docx` can open it;
- all expected tables and inline images exist;
- all image relationships point to real media parts;
- `REF`, `SEQ`, and bookmark fields exist for the expected references and captions;
- there are no unresolved labels/citations or manually duplicated heading prefixes;
- three-line table borders and repeated headers are present when requested;
- references are kept together and the final rendered page count is known;
- the source/reference-template hash or modification state was not changed unintentionally.

If Word has not updated field results during generation, open a copy in Word and run `Ctrl+A`, then `F9`, or use an equivalent field-update operation before the final render. Report this requirement to the user when it applies.

## Deliverables and communication

Deliver the final DOCX separately from the source and from any earlier version. Include a short QA summary naming the renderer, page count, field/cross-reference status, table treatment, and any unavoidable limitations. If a feature cannot be represented faithfully—custom macros, unsupported math, tracked changes, or a proprietary citation field—stop short of claiming a complete conversion and identify the exact limitation.
