# Source discovery and conversion architecture

## Inventory the project

Before creating a DOCX, identify:

- the main `.tex`, `.md`, or `.qmd` entry point;
- included source files (`\\input`, `\\include`, Markdown includes, or project manifests);
- figure and table assets, including PDF/SVG/PNG sources;
- `.bib`, `.bbl`, CSL, citation JSON, or manually written reference sections;
- custom commands/environments, theorem-like blocks, glossary/acronym files, and supplementary files;
- the requested output name and any existing DOCX template.

`inspect_latex_project.py` provides a conservative inventory. It is a preflight aid, not a full TeX parser; inspect the source when custom macros or generated content are present.

## Recommended intermediate representation

Convert the source into an ordered block model before writing Word. A useful conceptual shape is:

```text
Document
  metadata: title, authors, affiliation, abstract, keywords
  blocks: [Block, ...]
  labels: source_label -> target_id and kind
  citations: citation_key -> bibliography_number
  assets: source_path -> embedded_media_id

Block
  kind: heading | paragraph | list | equation | figure | table | reference
  source_location: file and line if available
  text/runs or structured payload
  label/caption if applicable
  style hints and pagination hints
```

The model prevents a common failure mode: converting the visible text successfully while losing the relationships that make the document maintainable.

## LaTeX route selection

Use a semantic converter first when it can preserve the required features. Pandoc is often effective for ordinary paragraphs, lists, citations, and basic math. It should not be trusted blindly for a heavily customized template, unusual table rules, or Word-specific field behavior.

Use custom generation or post-processing when any of the following matters:

- a supplied DOCX template must be matched closely;
- heading numbers must be generated by Word without duplication;
- figure/table/equation references must be live `REF` fields;
- tables need three-line borders and column-specific alignment;
- template styles contain inherited `keepNext` or `pageBreakBefore` settings;
- the source contains custom macros or environments that a generic converter flattens incorrectly.

A hybrid route is normally best for long papers: let the semantic converter handle ordinary prose/math, then use `python-docx` and OOXML for template styles, captions, bookmarks, fields, tables, and pagination.

## Parsing rules

- Use balanced-brace and environment-aware parsing for nested LaTeX commands. A single regex that assumes flat braces will corrupt `\\textbf{...}`, nested citations, and captions.
- Resolve `\\input` and `\\include` in source order, while preserving source locations for diagnostics.
- Normalize `~`, repeated whitespace, escaped punctuation, and source-only layout commands without changing visible meaning.
- Preserve inline semantic runs: bold, italic, small caps, code, hyperlinks, superscripts/subscripts, and math.
- Extract labels from figures, tables, equations, sections, and theorem-like blocks before rendering cross-references.
- Read bibliography data from the actual source database when possible. If the source contains a manually rendered bibliography, preserve its visible text but still create stable bookmarks for citations.
- Resolve relative asset paths from the file that references them, not only from the process working directory.
- Record unsupported commands and missing assets in a report. Never silently omit them.

## Template handling

When a reference DOCX is supplied:

1. inspect its section properties, styles, numbering definitions, theme fonts, and table styles;
2. copy or open it as the generation base;
3. remove or replace the document body content while preserving the intended style definitions;
4. explicitly override hidden paragraph properties that conflict with continuous flow;
5. validate that the original file's hash or modification time has not changed.

The template is a style source, not proof that its existing content is current. Never retain stale paragraphs, captions, references, or old numbering merely because they look correctly formatted.

When no template is supplied, create styles explicitly and record the assumptions. A reasonable academic default may use A4/letter page settings, readable margins, a serif body font, numbered heading levels, centered captions, and a smaller bibliography font, but these values are configurable rather than universal.

## Markdown route

For Markdown, detect ATX/setext headings, fenced code, block math, inline math, pipe tables, reference links, images, footnotes, and citation syntaxes such as `[@key]`. Do not confuse a Markdown pipe table with a layout table; convert it to a real Word table and then apply the requested borders/alignment. Preserve fenced code as a monospaced paragraph or a real code style, not as ordinary body text.
